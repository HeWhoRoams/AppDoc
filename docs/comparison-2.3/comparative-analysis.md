# AppDoc v2.3.0 — Comparative Analysis of Five Generated Documents vs. the HelpDesk Standard

**Reference standard:** `C:/Github/helpweb/Planning/HELP_DESK_APPLICATION_DOCUMENTATION.html` (2,675 lines, ~9,817 words, hand-written, CMU-branded HTML with mermaid diagrams, TOC sidebar, and a reproducible verification appendix).

**Targets analyzed:** flaskr-tdd, spring-petclinic, eShop, gitea, helpweb — all generated by AppDoc v2.3.0 (template 2.3), evidence date 2026-11-11.

**How to read this report.** For each target I give: Overview, Strengths, Weaknesses, Gaps (categorized as *code/stack*, *AI*, or *other*), Areas to Enhance, and Errors/Issues Found. The final section compares all five. I compare on **structure, depth, and usefulness** — not on whether the same content exists, since the standard is for a specific app (HelpDesk) and the targets are different apps. I am deliberately critical: this is input to a remediation plan.

A note on the standard's quality bar, which I use as the anchor throughout:
- **Every claim carries evidence**, and the standard goes further with a **Verification Appendix (section 18)** of *exact reproducible commands per claim*.
- **External Call Register (8A)**: a 23-row database-connection register, a stored-procedure/command register, a direct-SQL table/view register, an HTTP/XML/cross-app call register (HTTP-01…HTTP-05), an email/COM/file-system boundary register, and a failure/fallback/observability register.
- **Stored-procedure data dictionary (8B)**: parameter signatures *and* return codes for each procedure.
- **Role-to-capability matrix (5.3)**, **Troubleshooting Matrix (9)**, **Operations Runbook (17, five subsections)**, **Glossary (13)**, and explicit **Unknown** tracking.

The targets instead have: generated `entry-points` / `config-reference` / `scheduled-jobs` blocks, a curated `16.6 Configuration reference`, and an **Appendix A Evidence Register** with **A.4 verification commands** (PowerShell + POSIX per row). The single most important structural difference: **the targets' A.4 commands are auto-generated and frequently cite the wrong file or a pattern that does not match the claim** — a systemic weakness I flag in every document below.

## 1. flaskr-tdd

**File:** `c:\Github\appdoc-test\flaskr-tdd\docs\appdoc-2.3\application-documentation.md`

### 1.1 Overview
- **Size:** 1,218 lines, ~12,340 words.
- **Stack/language:** Python / Flask (`python-flask` stack, supported).
- **Completeness vs. standard:** Proportionate to a small app. It has all 16 sections + Appendix A, 8 features (F-1…F-8), 3 UI screens, 6 workflows, 10 findings (V-1…V-10), 7 open questions, 10 recommendations, 7 config keys, and a 95-row evidence register (80 Supported, 11 Corrected, 1 Downgraded, 1 Dismissed, 2 Answerable). For an app this size it is *dense* — arguably over-documented relative to its complexity, which is a strength, not a defect.

### 1.2 Strengths
- **Empirical verification beyond static reading.** Finding **V-9** (the test suite drops the application database) was *verified by actually running pytest on a scratch copy* (Flask 3.0.0, Flask-SQLAlchemy 3.1.1). No other target does this. This is the single most valuable verification behavior in the whole set and exceeds the standard, which is entirely static.
- **Honest severity calibration.** V-1 (hardcoded login creds) and V-2 (hardcoded `SECRET_KEY`) are Critical; V-3 (stored XSS via the `safe` filter) is High; V-4 (GET delete + no CSRF) is Medium. The impact column explains *why* each severity was chosen.
- **Clean, small, and fully resolvable.** Because the app is small, nearly every claim resolves to a real line, and the register is small enough to be credible. The "Dismissed" row (1) shows the audit actually rejected a claim rather than rubber-stamping it.
- **Good "Unknowns that must not be treated as controls" table (10.2)** — mirrors the standard's discipline of not assuming controls.

### 1.3 Weaknesses
- **No stored-procedure / external-call data dictionary.** The standard's 8A/8B (connection register + procedure signatures + return codes) has no equivalent. flaskr has few external calls, so the gap is small, but the *pattern* is absent.
- **UI catalog is thin (3 screens).** The standard's UI catalog (section 6) describes visible controls, states, and effects in detail. flaskr's UI-1…UI-3 are one-line entries.
- **Operations runbook (16.x) is minimal.** There is no rollback/backup/restore procedure (correctly marked Unknown), but the standard's runbook (section 17) has five subsections with concrete operator responses.
- **Architecture explanation is a component list, not a narrative.** The standard's section 3 explains *how* components interact; flaskr's 3.1 is a bullet list.

### 1.4 Gaps (categorized)
- **Code/stack:** None significant — Flask is fully supported and the app is small.
- **AI:** The narrative sections (2.2 purpose, 3 architecture) are competent but generic; they read like a template fill rather than an explanation. The "why this app exists" is thin.
- **Other (structural):** Missing the standard's 8A/8B external-call and procedure-dictionary sections; missing a rich per-subsystem inventory (the standard's 4A).

### 1.5 Areas to Enhance (prioritized)
1. **Keep and generalize the empirical-verification behavior** (V-9). This is the highest-value differentiator; make it a first-class, repeatable step for any finding that is cheap to run.
2. **Add an external-call / data-access register** even for small apps (connections, procedures, return codes) to match the standard's 8A/8B.
3. **Deepen the UI catalog** with visible controls and states, not just route names.
4. **Expand the operations runbook** with concrete operator responses for the failure modes in 16.4.

### 1.6 Errors/Issues Found
- **C2 regression (implementation-phase, fixed):** a bare `.gitignore` *prose mention* (not a citation) was parsed as a citation without a line number, triggering a C2 validation failure. Fixed by rewording the prose. This is a **citation-parser** bug: prose that names a file path is being treated as a citation. It is a systemic risk in any document that mentions file names in running text.
- No broken citations or factual errors found in the final document.

## 6. Cross-Document Comparison

### 6.1 Common strengths across all five
1. **Consistent, disciplined template.** All five use the same 16-section + Appendix A structure, the same *Cited / Inferred / Unknown* verification model, and the same "secret values never reproduced (value omitted)" rule. This consistency is itself a strength — a reader can navigate any of them the same way.
2. **Citation discipline.** Every factual claim carries a path-and-line citation, and the evidence register (Appendix A) records an independent source-to-claim audit with per-row results (Supported / Corrected / Downgraded / Answerable). The "Corrected" and "Downgraded" rows prove the audit is real, not a rubber stamp.
3. **Honest Unknown tracking.** All five have a "10.2 Unknowns that must not be treated as controls" table and a section 14 of open questions with owner/priority. None of them assume a control exists just because it is plausible.
4. **Security findings with calibrated severity and "Level set by" impact.** All five produce findings that explain *why* a severity was chosen, which matches the standard's rigor.
5. **Operations runbook (16.x) with a consistent shape** (platform, data stores, session/auth, failure modes, deployment/change, config reference, scheduled jobs).
6. **Mermaid diagrams and a glossary** in every document.

### 6.2 Common weaknesses / gaps across all five
1. **A.4 verification commands are auto-generated and frequently cite the wrong file or a non-matching pattern.** This is the single most consistent defect. The standard's section 18 gives *exact reproducible commands per claim*; the targets' A.4 attempts the same but is unreliable (flaskr E-8, spring E-55, eShop E-15/E-18, gitea and helpweb instances). As it stands, A.4 is *less* trustworthy than the standard's verification appendix.
2. **No stored-procedure / external-call data dictionary equivalent to the standard's 8A/8B.** None of the five gives parameter signatures + return codes. helpweb comes closest (caller-side procedure inventory) but cannot fill 8B because the procedures are not in the repo. eShop and gitea have external-call lists but not the standard's failure/fallback/observability depth per call.
3. **Generated `config-reference` blocks are noisy.** All five include non-app keys (CI vars, editor settings, fixtures, locale files, `desktop.ini`). gitea and helpweb are worst. The curated table below each generated block is good, but the generated block dilutes it.
4. **UI catalogs are source-only and thin on rendered controls/states.** All five list routes and handler names but not the visible controls, states, and effects the standard's section 6 describes.
5. **Role-to-capability matrices have many `?` cells** (gitea, helpweb especially). The standard's matrix is fully populated.
6. **Operations runbooks are thin on rollback/backup/restore** — correctly Unknown in most, but the standard's section 17 has concrete operator responses.
7. **Architecture explanation is a component list, not a narrative.** The standard's section 3 explains *how* components interact; the targets' 3.1 is mostly bullets.

### 6.3 Which document is closest to the standard?
**helpweb.** It is the *same application* the standard documents, and it has the deepest security analysis (24 findings, 5 Critical), the most detailed workflows (11, with the verification-method mechanics), the 19-row connection register (closest to the standard's 8A.1), and the largest evidence register (235 rows). Its main shortfall vs. the standard is the stored-procedure data dictionary (8B), which it *cannot* fill because the procedure bodies are not in the repository — a data-absence gap, not a tooling gap. If the procedures were added to the repo, helpweb would be the document most able to reach the standard's bar.

### 6.4 Which document has the most unique value?
