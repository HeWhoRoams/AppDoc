## 1. Verdict

Revision 1 traces every finding to a phase and its extractor diagnosis is correct. Its weakness is the *kind* of fix it chooses. Most findings get a template comment plus a SKILL.md sentence, and the comparison report already records what happens to that kind of fix: "the docs were regenerated after the first audit, but the same classes of gaps re-emerged." Where revision 1 does add enforcement, it parses free prose and AI-written Markdown with string patterns, which is fragile and partly throwaway.

The goal behind the findings is: **the Reader can trust the document, and the document stays true as the code changes, on any harness and any model.** Three structural changes serve that goal better than sixteen local patches:

1. **Scripts own everything that can be counted or enumerated.** The recurring factual errors (17 of 30 cron tasks, five controllers instead of six, 47 claims vs 43 rows, 1288 vs 1220 files) are all hand counts or hand enumerations.
2. **One template contract that the Check reads.** Columns, IDs, allowed values and cross-references are checked from a single spec instead of hard-coded section numbers and ad hoc sub-rules.
3. **The Evidence Register is data, not Markdown.** Counts, coverage and the appendix are computed from it, and each row carries an anchor the Check can verify against the cited lines.

## 2. Findings

Severity: **A** blocks the goal or ships a defect; **B** is a bandaid that will need redoing; **C** is a plan defect that is cheap to fix.

### A1. `verification.md` is never secret-scanned, and it is published
`check.py` runs `find_secret_shapes` on the Narrative only. `render/page.py` appends `verification.md` to the HTML as Appendix A. Re-run commands are exactly where a pattern such as a password literal is likely to be pasted. Revision 1 adds C10 over this file but no secret scan. This breaks the rule that secrets are never exposed and exists today in 2.1.
**Fix:** scan every file that is rendered or committed (register included) under C6.

### A2. The scan fix patches one folder name; the same bug remains in the same repo
`ALWAYS_IGNORE_DIRS` prunes by name at any depth. Revision 1 special-cases `packages`. But gitea's root `build/` folder holds tracked Go source (`generate-bindata.go`, `generate-openapi.go`, `openapi3gen/`, …) and is still pruned after the fix; it does not appear in gitea's Facts summary at all. `bin`, `out`, `dist`, `target` and `vendor` have the same exposure. Root-only is also wrong in the other direction: a NuGet `packages` folder sits beside the `.sln`, which is not always the Target root.
"Further considerations 2" in revision 1 names this and defers it. Listing skipped folders tells the AI to go and read them by hand, which is the manual step extraction exists to remove.
**Fix:** prune on evidence, not on name alone (section 4, P1).

### A3. `config_key` Facts are mostly not configuration, and 16.6 is built on them
`generic.py` treats every `.properties`, `.yml` and `.yaml` file as config. Verified against the Targets:
- spring-petclinic: three `application*.properties` files hold the real settings. The other sources are 11 `messages*.properties` i18n bundles, 2 build-wrapper files and 8 YAML files (CI workflows, k8s, compose, gitpod). The "641 config keys never surfaced" in finding X14 is largely UI message keys and CI syntax.
- gitea: 12,547 `config_key` Facts, with an 8,452-line `pnpm-lock.yaml` among the sources, while the real configuration (`custom/conf/app.example.ini`) yields none because INI is out of scope.

Revision 1's "Config files" table sorts by key count, so lockfiles and message bundles would lead it, and the new required 16.6 would have no Facts behind it for the largest example.
**Fix:** classify config sources before surfacing them; add an INI reader (section 4, P1).

### A4. Most findings are fixed by guidance only
X4, X5, X6, X7, X8, X9, X10, X11 and X15 are closed by template comments and SKILL.md rules. Nothing fails if 10.1 has no Severity column, if 14 is still a bullet list, if 15 skips the 10.2 controls, or if 16.5 lacks the operator rows. These are structural and machine-checkable, so by D1's own rationale they belong in the Check. This is the main reason to expect the gaps to re-emerge a third time.
**Fix:** check tables, enumerated values and ID references from a template spec (section 4, P2–P3).

### A5. Hand-authored counts and enumerations are a root cause that no phase addresses
The "N of M shown" rule asks the AI to state M, which is the number it gets wrong. The summary line in C10 asks the AI to write three counts and then fails it when they drift. The section 1 TOC is hand-written although `render` already generates a TOC from headings.
**Fix:** generate what can be generated; verify stated numbers against Facts; stop asking for duplicated data (section 4, P4–P5).

### B1. C10 parses an AI-written Markdown file with exact-string rules
- The fixed line `**Summary:** N rows: S Supported, C Corrected, D Downgraded.` is derivable from the table. It exists only to be checked against it.
- Banning "previous version" and "earlier draft" is a two-phrase blacklist. It is evaded by any synonym and it false-fails legitimate claims (an upgrade or migration row in gitea's register can say "previous version").
- "At least one row per section" rewards a single filler row. eShop already lumps all of section 6 into one row (E-67).
- Re-run commands are shell-specific (E-17 broke on an unescaped parenthesis); revision 1 answers with more guidance.

The direction already approved for the performance work — claim files as JSON Lines, provenance in its own file, script-rendered Generated blocks — makes this Markdown parser throwaway. Revision 1 does not mention that work.
**Fix:** register as JSON Lines, appendix and counts rendered from it (section 4, P4).

### B2. D2 and C9c contradict each other, and D2 is a loophole
C9c hard-fails unless section 1 mentions Appendix A. D2 lets `verification.md` be absent, in which case `render` produces no appendix. The template's "How to read" line already asserts the appendix exists unconditionally. Separately, revision 1 notes that a writer can skip the file to avoid C10; with the "stop after 3 failed checks" rule, deleting the audit becomes the easy way to pass.
**Fix:** the audit state is always declared: a valid register, or an explicit "audit not performed" that the HTML shows as a banner. A silent absence fails. A missing audit can still be allowed by policy (section 5, decision 3).

### B3. D4 is not enforceable and not portable
"A fresh agent/context that did not write the document" assumes sub-agents. AppDoc targets Copilot in VS Code, Cursor, Codex and local models, where they may not exist, and nothing records whether the rule was followed.
**Fix:** define independence by inputs (the auditor receives the document and the Target, not the writer's notes), give a fallback (a new session; the register is a file, so the audit resumes), and record `auditor: independent | same-session` so the Reader sees which it was.

### B4. The upgrade path breaks every downstream repo, with a misleading message
`ci/appdoc-docs-gate.yml` checks out `HeWhoRoams/AppDoc` with no ref and diffs `facts.json` byte for byte. Any extractor change, including P1, turns every adopter's gate red with "the code changed since the docs were last generated", which is false. Each template revision likewise fails every committed document. Check constants (`SECTIONS`, `REQUIRED_SUBSECTIONS`) hard-code the numbering; D5 accepts "no renumbering" as a constraint for that reason.
**Fix:** pin the skill ref in the gate template; compare `schema` first and report "AppDoc upgraded, re-extract" as its own outcome; stamp the template version in the Narrative so an old document gets one clear upgrade message.

### B5. The measurement is contaminated
Phase 6 hands the writer the per-repo answers ("six controllers, not five", "all 30 cron tasks"), then Phase 7 scores the same four repos with LLM judges. That cannot separate "the skill improved" from "the answers were supplied", and "closed or partly closed" cannot fail. None of the four examples is Classic ASP or Web Forms, the stacks AppDoc exists for first.
**Fix:** regenerate blind; add a held-out Target; add mechanical metrics (section 4, P7).

### P1 — Extractor correctness
**Files:** `scan.py`, `extract.py`, `facts.py`, `summary.py`, `stacks/generic.py`, `check.py` (C6), tests.

1. **Evidence-based pruning.** Replace the flat name set with a small rule table: a folder is pruned when its name matches *and* a marker confirms it is build output or a dependency cache.

   | Name | Pruned when |
   |------|-------------|
   | `.git`, `.svn`, `.hg`, `.vs`, `.idea`, `__pycache__`, `.venv`, `venv`, `.gradle`, `node_modules` | always |
   | `bin`, `obj` | a `*.csproj`, `*.vbproj` or `*.sln` is in the parent or an ancestor up to the Target root |
   | `target` | the parent holds `pom.xml` or `Cargo.toml` |
   | `build` | the parent holds `build.gradle*` or `CMakeLists.txt` — otherwise scanned (gitea's root `build/` is then scanned) |
   | `dist`, `out` | the parent holds `package.json`, `tsconfig.json` or a `*.csproj` — otherwise scanned |
   | `packages` | it holds `*.nupkg` or `repositories.config`, or the parent holds `packages.config` or a `.sln` |
   | `vendor` | it holds `modules.txt` (Go) or `autoload.php` (Composer), or sits under a `Gemfile` as `vendor/bundle` |

   The decision uses the tree only, so Facts stay byte-identical with or without `.git` (a git-tracked-files test was considered and rejected for that reason). `.appdocignore` gains `!name` to re-include, so an owner can override either way.
2. **Reconciliation, not a list to go and read.** `target` records each prune that removed files: path, rule, file count. The summary prints `files found = scanned + pruned + ignored` and a "Folders not scanned" table. The gitea 1288 vs 1220 question is then answered by the Facts.
3. **Config classification.** Each `config_key` gets a `role`: `app`, `build`, `ci`, `orchestration`, `i18n`, `lockfile`. Lockfiles and message bundles stop producing `config_key` Facts. Add an INI reader (keys and sections, never values). The summary's "Config files" table lists `app` sources first and shows the others as one count line.
4. **Schema.** One bump to `appdoc-facts/3`, agreed with the performance work so there is not a `/3` and a `/4` a week apart.
5. **C6 scans every published file.**

Tests: nested `src/packages/x.py` scanned; a NuGet `packages/` with `.nupkg` pruned and counted; a root `build/` with source and no build manifest scanned; `!build` re-include; petclinic-shaped sample yields `app` keys only from `application*.properties`; INI sample; determinism tests unchanged.

### P2 — Template contract
**Files:** `appdoc/template_spec.py` (new), `assets/template.md`, tests.

1. `template_spec.py` is the single description of the document: per section and subsection, the title, the table columns if any, the ID prefix, columns with allowed values, and required row labels. `check.py` derives `SECTIONS` and `REQUIRED_SUBSECTIONS` from it. A test asserts `template.md` and the spec agree.
2. The Narrative carries a version stamp (`<!-- appdoc:template 2.2 -->`). A missing or older stamp is one C3 problem that names the upgrade notes, instead of a wall of failures.
3. Every guidance comment starts `<!-- appdoc:guide`.
4. Template changes from revision 1, with these differences:
   - **8.5** becomes `ID | Timeout and retry | On failure | Observability`, keyed by the 8.1 and 8.3 IDs. 8.3 is unchanged.
   - **Section 1** keeps the support cross-reference table only. The TOC comes from `render`, which already builds one, and it includes Appendix A when the appendix exists. X16 disappears and C9c is not needed.
   - **16.6** and the **2.1** scan statistics are Generated blocks (P5), not hand-filled.
   - **8.4 field tables** and the `erDiagram` stay as guidance in 2.2. They need an entity/DDL extractor to be reliable; schedule that as its own item (a generic `CREATE TABLE` reader is cross-stack and matches the reference's stored-procedure dictionary).
   - The severity rubric is the default in the spec; an organization can replace it in `appdoc-context.md`.

### P3 — Check rules driven by the spec
**Files:** `check.py`, `tests/test_check.py`.

| Rule | Fails when | Closes |
|------|-----------|--------|
| **C9 Tables conform** | a table's header differs from the spec; a row's cell count differs from its header; an enumerated cell holds another value (Severity, 10.2 Status, Priority, Result); a required row label is missing (16.5); a guidance comment remains in the raw file | X4, X5, X7, X9, X10, X11, X13, flaskr glossary row |
| **C10 References resolve** | an ID repeats in its table; an ID reference or a Markdown anchor points at nothing; a 10.1 ID is addressed by no row of 15; a 10.2 control that is not `Present` is addressed by neither 15 nor 14; an 8.1 or 8.3 ID has no 8.5 row; a 4.1 `Features` ID is not in 4 | X8, X10, eShop F-18 class (existence), C5 above |

| **C6 No secrets** (extended) | a secret shape appears in any published file | A1 |

`fired()` in the tests moves to `C\d+`; report ordering sorts rule numbers numerically.

### P4 — Evidence Register as data
**Files:** `check.py`, `render/page.py`, `SKILL.md`, tests.

1. The register is JSON Lines in `docs/appdoc/` (name per the earlier claim-file decision). One row: `id`, `ref` (the document ID or workflow number it covers, e.g. `10.1/F1`, `7.3`), `claim`, `result` (`Supported | Corrected | Downgraded`), `cites`, `anchor` (a literal string that appears in the cited lines), `limitation`. A header record holds `auditor` (`independent | same-session`) and the declared scope.
2. `render` produces Appendix A from it: the table, the computed counts, and computed coverage per section ("section 4: 20 of 52 IDs"). No hand-written summary line and no free-text Corrections section, so X2 and X3 have nowhere to occur.
3. **C11 Register valid** fails when: a row does not parse; an ID repeats; `result` is not allowed; `ref` does not resolve to a document ID; a 10.1 ID or a workflow has no row; **an `anchor` is not found within its cited line span** (whitespace-normalized, stdlib only, no command execution).
4. The anchor check is the one new accuracy control in this release. It turns "the citation resolves" into "the cited lines contain what the row says they contain". In CI it also identifies *which* claims went stale after a code change, which is the basis for refreshing parts of a document instead of all of it.
5. Coverage beyond the mandatory sets is reported, not failed. A per-section pass/fail rule produces filler rows.
6. Audit state is always declared (finding B2). `check --require-audit` makes a missing audit a failure for teams and CI that want it.
7. Re-run commands become optional. `render` can print `grep -nF` and `Select-String -SimpleMatch` forms from `anchor` and `cites`, so they are never hand-escaped.

### P5 — Generated blocks (minimal)
**Files:** `appdoc/fill.py` (new), `__main__.py`, `check.py`, tests. Records the already-assigned **ADR 0005**.

- `appdoc fill <target>` rewrites the content between `<!-- appdoc:generated NAME -->` markers from `facts.json`. It is idempotent.
- Two blocks in 2.2: `scan-coverage` in 2.1 (stacks, counts, folders not scanned, reconciliation) and `config-reference` in 16.6 (`Key | Defined at | Secret location`, `app` role only, grouped by file). The AI adds an "Effect" note only for keys a workflow or finding depends on.
- The Check fails when a block differs from what `fill` would write, and exempts block rows from C5.
- This is also the mechanism for the approved mechanical docs refresh in CI.

### P6 — Guidance, docs, gate
- `SKILL.md`: shorter than revision 1's version, because table shapes, value sets and reference rules now live in the spec and the Check. Keep the judgment rules: severity reasoning, verified-absent vs not established, mining test suites, operator content for 16.5, the audit procedure with its fallback.
- `CONTEXT.md`: **Severity**, **Verified absent**, **Configuration reference**, **Generated block**, **Anchor**, **Template spec**.
- ADRs: 0005 Generated blocks; 0006 template spec and what the Check may verify (structure, references, numbers against Facts, anchors — never meaning); 0007 register as data and declared audit state (replaces revision 1's D2).
- `ci/appdoc-docs-gate.yml`: pin `ref:` to a release tag; compare `schema` before diffing and report an AppDoc upgrade separately; "C1–C8" → "C1–C11".
- `README.md`, `docs/docs-as-code.md`, `CHANGELOG.md` (with upgrade notes for 2.1 documents).

### P7 — Evaluate
1. `install_skill.py`, verify by hash, re-extract all four Targets.
2. Regenerate **blind**: the writer gets the skill only, not the per-repo fix list. The list in revision 1 Phase 6 step 4 becomes the answer key.
3. Score mechanically first: Check problems by rule on the frozen 2.1 fixtures (must fail) and on the new output (must pass); how many answer-key errors recur; register coverage per section as computed by `render`.
4. **Seeded-error test for the audit:** insert ten known-false claims with resolving citations into a passing document, run the independent audit, record how many it catches. This is the only measure of whether the audit works.
5. Add a held-out Target that no plan or prompt has described. `C:\Github\helpweb` is the obvious one: the reference standard documents that codebase, so AppDoc's output for it compares like for like, on Classic ASP. Keep it out of the public examples.
6. Then the four LLM comparison reports, as a qualitative supplement.
